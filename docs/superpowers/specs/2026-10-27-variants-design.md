# Seasonal variants: design

Status: draft for Brian's review, 2026-10-27.

## Why

Brian wants the Frame TV to get into the spirit of a season: for Halloween,
artworks with Halloween elements painted in, mixed in with the normal works. A
dry run on 2026-10-27 (4 works on the TV, 3 models, 3 strengths) settled the
look and the tool:

- **Model:** `google/gemini-nano-banana-2.1` through OpenRouter. It was the best of
  the three, and the cheapest of those that produced 4K: about $0.12 and 30 s per
  edit, returning 5504x3072. Gemini 3.1 Flash Image cost more ($0.15) and added
  junk, such as made-up text painted on a boat; GPT-5.4 Image cost $0.28, took
  83 s and stops at 2560px.
- **Strength:** "obvious", a full Halloween makeover in the original's style. The
  "subtle" level could not be seen at all, and "noticeable" was fine, but Brian
  found "obvious" the most fun.

The prompt that produced the chosen result is in the appendix.

The point is delight, and with as little upkeep as possible: Brian puts
Halloween in the mix, the TV gradually fills up with Halloween versions, and he
can fix any single one he doesn't like.

## Goals

- A work can have **variants**: the original plus any number of themed versions,
  all hanging off the work's existing key. A work's page shows all of them.
- **Variant types** (e.g. "Halloween") are managed in the web UI, each with a
  default prompt.
- A higher-level **mix** says what share of the TV should be originals and what
  share each variant type: e.g. originals 50%, Halloween 50%. It is set by hand.
- Variants are **generated automatically**, throttled, during the nightly run,
  so that the TV approaches the mix. They can also be generated by hand.
- From a work's page Brian can **regenerate** a variant, with the prompt box
  pre-filled with (and showing) the type's default prompt, which he may edit.
  He can also mark a variant "don't use".
- Every generation's cost is recorded and shown.

## Non-goals (for now)

- **A calendar for the mix** (e.g. Halloween fades in on Oct 1, out on Nov 1).
  Wanted later. The mix model should not make this awkward, but nothing is built
  for it now.
- **Favourites.** Parked; not clear yet what they would add over the collection.
- **Variants for works that are not on the TV.** They would never be seen.
- **Getting variants onto the TV for Halloween 2026.** This build is not expected
  by Friday 2026-10-31.
- Changing the library model beyond what variants need. The decisions below
  record how it stands so variants fit into it.

## Anti-goals

- **A bad edit reaching the TV unnoticed with no way to fix it.** The model
  sometimes changes things it shouldn't (it turned an oar in Homer's *The Herring
  Net* into a mast hung with netting). There is no approval gate, by Brian's
  choice, so the fix has to be quick: "don't use" or regenerate from the work's
  page, and the TV follows on the next sync.
- **Surprise spending.** The throttle bounds each night; all costs are logged.
- **Churn on the TV.** A work does not flip between original and variant from
  night to night: every swap is a delete plus an upload on the TV.

## Library model (as decided)

These stand as they are today; variants slot in alongside them.

| Concept | Meaning |
|---|---|
| Catalogue | Every crawled work, one key per work (e.g. `aic:25865`). |
| Rejected | Works the renderer refused automatically. Never shown. |
| Collection | Works Brian would like to see more of. A **preference, not a gate**. The three "choose from" modes stay: collection first then automatic picks (default), collection only, automatic. |
| Banned | Never published, and taken off the TV if live. Also hides a work while browsing. There must be a way to list banned works and unban one (the catalogue's status filter may already do this; check). |
| Pinned | Published soon and never retired. |
| **Variant** | New: a themed version of a work. |
| **Variant type** | New: a theme with a default prompt. |
| **Mix** | New: shares between originals and variant types. |

## Concepts

### Variant type

A name (e.g. "Halloween"), a slug (`halloween`), and a default prompt. Managed on
a new variant management page. A type has no on/off switch and no ratio of its
own: it is active when it has a share in the mix.

### Variant

One generation for one work and one type: the work's key, the type, the prompt
actually used, the model, the cost, when it was made, and the file.

Each (work, type) has at most one **current** variant. Regenerating makes a new
variant that becomes current; the old one is kept and can be made current
again.

**Don't use** applies to the (work, type) pair, not one generation: the work
shows its original for that type, and the nightly run does **not** generate a
replacement. Getting a new one is an explicit regenerate from the work's page,
which clears "don't use". *(Claude's call: otherwise a work Brian wanted left
alone would be paid for again every night.)*

### Mix

A list of shares adding up to 100%: one for "original" and one per variant type
in the mix. Originals 100% is "no seasonal art". Set by hand on the variant
management page.

The mix is a **target**, not a guarantee. A work with no current, usable variant
for a type shows its original. The variant management page shows, per type, the
share asked for, the share live now, and how many works on the TV have a usable
variant, e.g. "Halloween: 50% wanted, 12% live, 9 of 75 needed".

## Behaviour

### Which version of each work the TV holds

The TV holds **one version of each work**: the original or one variant, never
both.

**Every live work is eligible** for a variant slot: paintings and photographs,
pinned and collection works alike (Brian, for now).

When the mix changes, or a work goes live, frame-art assigns each live work a
**slot**: original, or a variant type. It aims to match the mix shares across
the works on the TV. A work keeps its slot while the mix keeps that type (no
night-to-night flipping). When a type leaves the mix, its works go back to
original. When a type's share goes down, frame-art moves only as many works out
of it as needed.

A work in a variant slot shows its current, usable variant if it has one, and
its original otherwise.

A variant made or made current **by hand** puts its work in that type's slot
(if the work is live and the type is in the mix), even if that takes the type
past its share. *(Claude's call: generating one by hand and not seeing it would
look broken.)*

**When a mix change takes effect:** at the next nightly run, which reassigns
slots. Moving works back to original costs no edits, so it is not limited by the
nightly limit. *(Claude's call.)*

Swapping a work between versions uses the existing machinery: retire the old
file, publish the new one. HA's sync automation uploads the new file and deletes
the old content id, as it does for any retirement. No Home Assistant changes are
expected; confirm against `docs/ha-automation.yaml`, in particular the delete
allow-list and the `^MY[_-]F?\d+$` content-id filter.

Retirement by pool size and bans work on works, not versions: a work retired
from the pool takes whichever version it had with it.

### Generation

**Automatic, in the nightly run**, after choosing the night's new works:

1. Work out the slots (above).
2. List works in a variant slot that have no current, usable variant of that
   type.
3. Generate for them, **new arrivals first** (they will be live longest), then
   the rest in random order, up to the **nightly limit**.
4. Render each new variant through the normal pipeline and publish it in place
   of the work's original.

**Nightly limit:** a number of edits per night, in Settings (Brian's
suggestion was "throttle things a bit"; 10 is the proposed default, about
$1.20). The variant management page shows the cost so far.

**By hand:**

- On the variant management page: run a type over a chosen set of works. This
  counts outside the nightly limit, shows the estimated cost before starting,
  and runs as a job on the runs page.
- On a work's page: generate or regenerate one type. The prompt box is
  pre-filled with the type's default prompt, which stays visible as the default
  if Brian edits it.

**Failures:** a failed or empty generation is logged on the runs page and tried
again on a later night. The work keeps its original meanwhile. After 3 failed
attempts for a (work, type), automatic generation stops trying it and the variant
management page lists it; generating by hand still works. Every attempt counts
toward the nightly limit. *(Claude's call.)*

### What is edited

The model edits the **work's source image**, not the 16:9 TV render, and the result then goes through frame-art's normal render to
16:9. Editing the render made the model paint over the blurred fill around
portrait works and extend the scene to the edges, and it added a fake "Claude
Monet" signature (seen in the dry run). Whether rendering a variant needs the
crop/fill rules adjusted (the output's aspect ratio may differ from the
source's) is for the builder to check.

frame-art does not keep sources today: `pipeline.fetch`/`load_work` download at
the width the render needs (often 2000-3000px), trim scan borders, render, and
discard. For variants: fetch the source the same way, **after trimming** (so the
model never sees scan cards or colour bars), and keep it in the data folder at
`sources/<work>.jpg` (JPEG quality 95) so regenerating doesn't download again.
The model's output (5504px) is larger than that input either way. *(Claude's
call.)*

## Storage

Two places, as today:

- **frame-art's private data folder** (`--data`): the database, and now
  variant files and the trimmed sources they were made from.
- **The pool folder HA uploads from** (`--dest`, served by HA at /local/): only
  finished renders going to the TV. Variant files never go here un-rendered.

**Variant files:** `variants/<type slug>/<work>/<n>.jpg` in the data folder, one
per generation. They are saved as JPEG at quality 95 (the model returns 5504px
PNGs of 20MB+). Brian's requirement: no noticeable loss of quality. Older
generations are kept.

**Database:** new tables for variant types and variants. The mix and the nightly
limit go in settings. `published` records which variant a published file is
(null for the original), so history, "now showing" and `sensor.frame_art_now_showing`
can say "Halloween version".

**Published filenames:** published files are never rewritten in place, because
the HA integration identifies uploads by filename and modified time. So every
variant needs a distinct name: the original's name plus `--<type>-<n>`, e.g.
`full/aic-25865-winslow-homer-the-herring-net--halloween-3.jpg`.

**The OpenRouter key:** read from `<keys dir>/openrouter/key`, as in
`docs/api-keys.md`. The keys mount for the deployed container is noted there as
not wired yet: it needs a homelab-stacks compose change, which goes to proxmox
for review as usual. The key never goes in settings, the repo, the bus or a log.

## Web UI

- **Variant management page** (new): variant types (add, rename, edit default
  prompt); the mix; the nightly limit; per-type progress against the mix; cost
  so far; "generate for…" by hand.
- **Work page** (new; there is no per-work page today): the original and every
  variant side by side, grouped by type, with current / older / don't use, each
  generation's prompt, model and cost; generate/regenerate with the prompt box;
  "don't use"; make an older generation current. Linked from the catalogue,
  pool, history and "now showing".
- **Now showing / history:** say when the TV shows a variant.

## Appendix: the dry-run prompt for "obvious"

> Turn this picture into a clearly Halloween version of itself: Halloween
> elements, mood and light throughout, while keeping the composition and the
> original style and medium recognisable, as if the same artist had made a
> Halloween edition.

Sent with `modalities: ["image","text"]` and `image_config: {aspect_ratio:
"16:9", image_size: "4K"}`.
